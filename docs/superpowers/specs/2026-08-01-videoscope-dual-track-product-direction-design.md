# VideoScope 双轨产品方向设计

状态：已通过对话评审，待用户审阅书面规范

日期：2026-08-01

适用范围：现有 v0.1 诊断底座之后的产品演进

## 1. 设计结论

VideoScope 保持一个代码仓库和一套可信媒体底座，同时形成三个清晰的
产品层：

- **VideoScope Check**：发现可观察问题，给出时间区间、证据和限制；
- **VideoScope Resolve**：围绕用户目标处理视频，交付新的可用文件；
- **VideoScope Lab**：为研究者和开发者提供 Detector、Benchmark、CLI、
  API、配置、插件和可复现实验能力。

产品采用两条同时推进的路线：

1. 专业与开源路线持续强化 Check 和 Lab，建立技术可信度、研究价值和
   GitHub 生态；
2. 大众结果路线以 Resolve 为入口，让用户不需要理解检测器即可解决
   “发布不了、视频坏了、内容太长、不能安全分享”四类实际麻烦。

两条路线共享媒体探测、时间轴、检测器、证据、任务配置、产物、隐私和
输出复检能力，不建立互相漂移的第二套分析实现。

## 2. 与现有 v0.1 的关系

现有 `docs/product-spec.md` 已冻结 v0.1，并明确把视频修复和自动编辑列为
非目标。本设计不追溯改变 v0.1，也不允许把 Resolve 功能伪装成 v0.1
能力。

进入 Resolve 实现前必须先完成一次正式产品范围变更：

- 保留 v0.1 CPU 诊断命令、报告和依赖边界；
- 为处理任务定义新的版本范围、配置模型和产物契约；
- 明确“检测结论”与“处理动作”是两类不同数据；
- 明确源视频只读、所有处理都写入新文件；
- 为处理记录、复检结果和人工确认建立独立 schema；
- 同步更新产品规格、架构、路线图、隐私说明和 CLI/API 文档。

现有 `AnalysisReport` 继续是诊断事实来源。Resolve 不得修改历史 Finding
来证明处理成功，而应保存处理前报告、处理计划、处理记录和处理后报告。

## 3. 产品原则

### 3.1 从目标开始，而不是从检测器开始

大众用户首先选择自己想得到的结果，系统再决定需要运行哪些分析和处理。
检测器名称、阈值和原始曲线默认收进高级视图；用户首先看到可理解的风险、
处理选择、前后预览和可下载产物。

### 3.2 必须交付实际结果

成功状态必须对应一个可播放、可下载且符合所选任务约束的新文件或内容包。
只生成问题列表、建议文字或“优化完成”提示，不算 Resolve 成功。

### 3.3 诊断、改善和生成必须分开表达

- **检测**：观察到什么现象以及证据在哪里；
- **处理**：执行了哪些确定性媒体操作；
- **改善**：某个明确指标在同一检测器和配置下如何变化；
- **生成或推断**：新增了源视频中不存在的内容。

界面、报告和变更记录必须使用这四种语义，不能把推断内容描述成原始信息
的恢复。

### 3.4 不使用未经校准的统一质量分

Resolve 可以显示平台兼容检查、任务完成状态、每个检测器内的前后变化和
人工确认状态，但不把不同检测器权重合成为“总体质量分”。“发布就绪”只
表示已通过一个有版本的发布 Profile，不表示视频艺术质量得到客观评分。

### 3.5 安全、可逆和可追溯

- 永不覆盖源视频；
- 内容改变前提供预览或明确确认；
- 输出 `changes.json`，记录动作、参数、工具版本和受影响区间；
- 输出后重新运行适用检查；
- 失败时保留可用的中间产物，但不把它们标成最终成功产物；
- 网络、模型下载和远程处理必须独立、显式授权。

## 4. 统一产品架构

```text
用户目标
  -> 任务模式 A / B / C / D
  -> 能力与隐私预检
  -> VideoScope Check 生成基线事实
  -> Resolve Planner 生成候选处理计划
  -> 预览与人工确认
  -> Media Executor 输出新文件
  -> VideoScope Check 对输出复检
  -> 交付产物、变更记录、限制和复检结果
```

### 4.1 核心组件

#### Task Router

把用户选择的目标映射到 A、B、C、D 任务，不执行媒体算法。任务可以串联，
例如 `C 内容整理 -> D 安全分享 -> A 发布即用`。

#### Capability Resolver

根据文件大小、编解码器、浏览器能力、已安装本地组件、模型权限和网络同意
选择执行后端。选择结果必须在开始前可见。

支持的能力层：

- `browser_local`：公开网站内可安全完成的小文件和轻量处理；
- `native_local`：复用 Python、FFmpeg 和可选本地模型，承担完整流程；
- `remote_opt_in`：未来可选，只有用户明确知晓上传内容、保留时间和服务方
  后才能使用。

若当前后端无法完成任务，产品必须给出可操作的本地安装或降级方案，不能
在静态网页上模拟成功。

#### Check Engine

复用现有探测、抽帧、镜头、Detector、Evidence 和报告流水线。处理前后
使用相同版本和配置比较可比较指标，避免用不同基线制造改善。

#### Resolve Planner

将目标 Profile、Findings、媒体元数据和用户锁定内容转换为有序动作。每个
动作声明：

- 动作 ID、版本和参数；
- 影响的时间、画面、音轨或元数据范围；
- 是否改变内容语义；
- 是否需要人工确认；
- 所需后端、模型、网络和资源；
- 失败后的降级或回滚策略。

Planner 只提出计划，不直接写文件。

#### Media Executor

按照确认后的动作顺序执行外部命令或受控 provider。外部命令继续使用参数
数组并禁止 `shell=True`。Executor 只写任务工作区和输出目录，使用临时
文件与原子重命名交付最终产物。

#### Verification Gate

重新探测和检查输出，至少确认：可解码、声明时长、音视频流、目标 Profile、
新增黑屏或冻结、字幕和裁剪边界、相关隐私风险。未通过的产物进入
`needs_review` 或 `failed`，不能显示为“已完成”。

#### Artifact Manager

统一管理视频、字幕、封面、报告、预览、变更记录和来源映射。公开分享包与
私有证据目录分离，所有报告只引用输出根目录内的相对路径。

### 4.2 建议的任务状态

```text
created -> inspecting -> planning -> awaiting_confirmation
        -> previewing -> processing -> verifying
        -> completed | needs_review | partial | failed | cancelled
```

状态变更要持久、可恢复并携带阶段说明。取消操作停止后续步骤、清理未完成
临时文件并保留用户明确要求保留的诊断或预览。

## 5. A：Publish Ready

### 5.1 用户承诺

用户说明要发布到哪里，VideoScope 交付可以直接发布的新文件，而不是只给
出参数建议。

### 5.2 入口

首屏按目的地选择：抖音/TikTok 竖屏、B站/YouTube 横屏、微信、
小红书/Instagram、课程、商品展示或“不确定”。每个平台规则由带版本的
`PublishProfile` 表达，不能散落在界面或转码代码中。

上传后立即显示：媒体摘要、处理发生在本机还是远程、预计输出数量、原文件
不会覆盖，以及当前设备能完成的能力。

### 5.3 处理流程

先运行快速兼容检查，再按需进行深入处理。计划分为：

- 可默认执行的低风险动作：兼容容器和编码、方向修正、元数据清理、独立
  字幕、封面生成、始终输出新文件；
- 必须确认的内容动作：裁剪、删除、烧录字幕、稳定、插帧、AI 增强、音乐、
  降噪和变速。

系统先生成短预览或代表帧前后对比，用户确认后才完整渲染。高级编码设置
默认折叠。

### 5.4 输出与验收

典型输出：

- `publish-ready.mp4`；
- `subtitles.srt`；
- 一个或多个封面；
- `changes.json`；
- `technical-report.json`。

成功要求：文件可下载和播放、通过所选 Profile、无新增严重黑屏或冻结、
字幕和裁剪通过复检、原文件未改动、内容修改已确认、失败时有可用降级路径。

## 6. B：Video Rescue

### 6.1 用户承诺

尽可能抢救或改善坏掉、拍差或导出异常的视频，并诚实区分“已修复”、
“已改善”和“无法恢复”。

### 6.2 症状入口

用户选择：打不开、中途停止、无声、过小或噪声、过暗、模糊、抖动、
卡住或掉帧、音画不同步、颜色异常，或“不知道哪里坏了”。

### 6.3 可恢复等级

1. **安全修复**：重封装、索引或时间戳、方向、有效轨道选择、可解码片段
   抢救和安全尾部裁剪；
2. **可改善但无法完全恢复**：暗部、噪声、抖动、模糊、闪烁、音频噪声、
   同步、掉帧和冻结；
3. **信息已丢失**：纯黑或过曝细节、严重压缩、缺失帧或数据、削波音频。
   只能抢救、裁剪，或在明确标注下生成插值内容。

提供 Conservative、Balanced 和 Aggressive AI 三种策略。默认使用
Conservative；Aggressive AI 必须单独启用并定位所有生成区间。

### 6.4 流程与输出

流程为：只读源文件与哈希 -> 扫描可解码区间 -> 候选方案 -> 代表性
5–10 秒预览 -> 用户比较 -> 完整处理 -> 复检。

即使无法恢复全部视频，也应交付可播放片段和精确损坏区间。典型输出包括
保真抢救版、增强版、摘要、`damaged-segments.json`、预览和变更记录。

成功要求：最大化保留原始可解码内容、输出可播放、来源和生成区域可追溯、
原件未改、经过复检，并且不使用“百分百恢复”等承诺。

## 7. C：Long Video to Useful Content

### 7.1 用户承诺

把长视频整理成可观看、可复用或可发布的内容包，而不是随机截取几个片段或
只返回一段摘要文字。

### 7.2 目标和视频类型

目标包括：60 秒短视频、3–5 分钟精华、章节、文字稿、会议行动项、课程
重点、直播高光、旅行或家庭集锦、商品片段和多平台内容包。

视频类型包括会议/采访、课程/演讲、直播、游戏、旅行/家庭、商品、教程/
屏幕录制、活动/体育和播客。每种类型使用独立选择逻辑，不共用一个无法
解释的“精彩度”分数。

用户可设置必须保留的关键词或主题、排除内容、目标时长和比例、是否允许
重排，以及时间轴锁定区间。

### 7.3 分层理解

- 基础层：镜头、静音、重复、黑屏、运动、响度和 OCR 变化；
- 语义层：语音转录、语言、匿名说话人 A/B/C、主题、问题、结论和行动项；
- 生成层：可选摘要、标题、章节名、描述和封面。

低置信度结果必须标记，生成层必须可关闭。不得进行真实身份识别。

### 7.4 内容地图和故事板

系统逐步给出元数据、章节、文字稿、建议删除段、候选高光和草稿。每个候选
片段包含源时间戳、代表帧、选择理由、置信度和关键词。用户在完整渲染前
编辑故事板。

提供 Faithful、Condensed 和 Creative Short 三种强度。默认 Faithful，
保留顺序和上下文；重排或可能改变语义时必须明确提示。

### 7.5 输出与验收

可输出竖屏 60 秒版、横屏精华、章节、文字稿、SRT、摘要、封面、
`source-map.json` 和变更记录。

成功要求：至少一个可用目标视频、必须保留内容存在、所有片段可追溯到源
时间、故事板可编辑、没有伪造引语或事实、输出通过黑屏、字幕同步、响度、
重复、裁剪和格式复检。

## 8. D：Safe Sharing

### 8.1 用户承诺

从画面、声音和元数据中发现分享风险，在用户确认后进行处理，输出经过复检
的分享副本。

### 8.2 风险入口

先询问分享对象：公开发布、陌生人、工作/客户、学校/家庭、外部 AI 服务、
证据用途或完整隐私扫描。不同场景使用有版本的风险 Profile。

检查范围：

- 画面：人脸区域、车牌、工牌、证件、银行卡、快递单、门牌和签名；
- 屏幕与文字：电话、邮箱、地址、账号、密码或验证码、聊天、浏览器标签、
  文件路径、通知、二维码、条码、地图和订单；
- 音频：姓名、电话、地址、账号、验证码和背景私密对话；
- 元数据：GPS、设备、时间、软件、标题、作者、文件名、缩略图和附加流。

检测人脸区域不等于判断身份。系统使用“Face track 01”等匿名轨迹，不建立
身份数据库。

### 8.3 复核与处理

风险按时间轴和通俗语言展示。跨帧遮挡必须跟踪区域并加入可配置保护时间；
置信度下降时扩大范围或暂停等待确认，不能静默停止遮挡。

用户可对视觉风险选择模糊、像素化、实色覆盖、裁剪、删除、手动画框或允许；
对音频选择静音、提示音、仅处理词语、变声、删除或保留。

### 8.4 私有证据和分享包

输出严格分离：

```text
privacy-review-private/
  风险地图、未脱敏证据、人工确认状态

share-package/
  share-safe.mp4、脱敏摘要、changes.json
```

分享包不得包含原始敏感文字、未脱敏证据、绝对路径、用户名、GPS、身份猜测
或内部缓存。

导出后重新检查可辨识人脸或车牌、遮挡中断、可读敏感文字、可扫描二维码、
可听敏感语音、元数据、字幕、封面和文件名。高风险公开发布仍要求人工最终
复核，产品不承诺“百分百隐私”或法律合规认证。

成功要求：脱敏副本可播放、源文件未改、用户确认风险均已处理、遮挡连续、
音频与元数据已处理、复检没有未确认高风险信号、私有证据未进入分享包。

## 9. 模式组合

四种模式不是孤岛：

- 长视频发布：`C -> D -> A -> 最终复检`；
- 损坏隐私视频：`B -> D -> 最终复检`；
- 仅平台适配：`A`；
- 仅分享脱敏：`D`。

组合任务共享一次输入哈希、媒体探测、时间轴和可复用特征。每个阶段保存
自己的计划、确认和产物，后续阶段不得静默改写前一阶段的选择。

## 10. 专业与开源路线：VideoScope Lab

Lab 与 Resolve 同时建设，目标是让大众结果有可信底座，并让仓库具有长期
研究和工程价值。

### 10.1 产品与发布基础

- 确保 README 安装和演示命令真实可运行；
- 发布有版本的 CLI、Python 包、本地 Web 和变更日志；
- 维护 Linux、Windows、Python 3.11/3.12 的离线 CPU CI；
- 提供真实示例报告、短演示视频和限制说明；
- 完善 GitHub Topics、仓库主页、社交预览和 Discussions；
- 建立问题模板、Detector 贡献模板和可复现误报/漏报流程。

### 10.2 Benchmark 和研究可信度

- 建立获得授权的真实生成视频人工标注集；
- 固定开发集与隐藏或冻结测试集，避免在同一素材上反复调阈值；
- 每个 Detector 分别报告 temporal IoU、事件 precision/recall/F1、边界误差
  和负样本误报；
- 发布数据范围、配置、平台、工具版本和限制；
- 不把合成 fixture 表现宣传成真实视频准确率；
- 不合成未经校准的跨 Detector 总分。

### 10.3 生态扩展

- 稳定 Detector、Provider、Profile 和处理动作协议；
- 提供 Python SDK、CLI 批处理和 JSON Schema；
- 增加 ComfyUI、生成流水线和剪辑工具集成；
- 提供小型、可复制的自定义插件示例；
- 用真实问题、修复前后和 Benchmark 变化持续发布技术内容。

GitHub Star 增长以可复现价值为核心，不使用虚假指标：访客应在 README 第一
屏看到真实效果、三分钟体验路径、支持范围、隐私边界和明确贡献入口。

## 11. 分阶段路线

### 阶段 0：稳固 Check 与 Lab

完成真实安装、发布、演示和人工 Benchmark 基础，修正文档与实际功能漂移。
现有 v0.1 行为必须保持兼容。

### 阶段 1：A Publish Ready MVP

优先交付低风险平台适配、预览、输出复检和真实可下载文件。该阶段形成最短
的大众闭环：

```text
上传 -> 选择平台 -> 自动处理 -> 复检 -> 下载发布文件
```

### 阶段 2：D Safe Sharing 与 B Video Rescue

先实现确定性和可解释动作，再逐步加入需要模型的识别、增强或跟踪。D 和 B
共享预览、区间处理、变更记录和复检基础设施。

### 阶段 3：C Long Video to Useful Content

在转录、章节、来源映射和故事板可靠后交付。先做忠实整理，再做可选生成和
创意重排。

### 阶段 4：高级 AI 与生态

加入显式标注的超分、插帧、生成式修复、语音增强、远程 Provider、工具插件、
团队分享和公开 Benchmark 扩展。

## 12. 错误处理与降级

- 输入无法读取：不创建伪产物，提供兼容性说明；
- 单个 Detector 失败：保留其他分析，计划标记不完整；
- 处理动作失败：停止依赖动作，保留已验证的独立产物；
- 输出复检失败：产物进入 `needs_review`，显示失败项和重新处理入口；
- 浏览器资源不足：释放帧缓存，允许切换原生本地后端或降低配置；
- 模型不可用：CPU 动作继续，AI 动作明确跳过或等待授权；
- 网络中断：本地任务继续，远程任务不得伪装完成；
- 取消：停止新动作、终止可取消进程、清理半成品并保留用户确认保留的结果；
- 部分抢救：交付可播放区间和损坏映射，状态为 `partial`。

所有错误信息必须脱敏，不显示绝对个人路径、令牌、未过滤外部命令输出或
服务端堆栈。

## 13. 测试与验收策略

### 13.1 契约测试

- 处理计划 schema、动作版本和确定性排序；
- 源哈希、产物哈希、来源映射和相对路径；
- 人工确认不能被默认值绕过；
- 旧 AnalysisReport 保持可读取；
- 浏览器、本地和未来远程后端的能力声明一致。

### 13.2 媒体处理测试

- 每个动作的正常、边界、失败、取消和跨平台路径；
- 包含空格、中文和 Unicode 的输入输出；
- 可变帧率、多音轨、旋转元数据、损坏时间戳和部分不可解码文件；
- 处理前后时长、音视频同步、帧范围和目标 Profile；
- 不一次性把完整视频读入内存；
- 外部命令参数数组和路径注入回归。

### 13.3 模式级端到端测试

- A 输出满足平台 Profile 且可播放；
- B 能抢救部分损坏输入并诚实标记未恢复区间；
- C 保留用户锁定内容并生成可追溯 `source-map.json`；
- D 遮挡连续、私有证据不进入分享包；
- A/B/C/D 输出都经过复检，失败不会显示为完成；
- 串联模式不重复解码且不丢失各阶段确认记录。

### 13.4 人工验收

- 不懂编码参数的用户能在三分钟内选择模式并开始；
- 用户能明确知道文件是否离开设备；
- 用户能比较预览、取消内容改变并找回原件；
- 结果文件可在目标应用中实际打开或发布；
- 高风险隐私和生成式处理有明确人工确认；
- 桌面、移动和中英文界面均能理解任务状态。

真实视频的效果指标必须来自独立标注集和实际执行，不能在规范中预先写入
准确率、提速倍数或满意度数字。

## 14. 产品指标与隐私

默认不启用遥测。用户显式同意后，只收集不含视频、帧、音频、提示词、路径
或报告正文的任务级事件，例如模式、匿名能力层、阶段成功/失败和用户是否
下载产物。

核心产品指标：

- 开始任务到获得首个预览的时间；
- 完成并下载可用产物的任务比例；
- 复检一次通过率和 `needs_review` 原因；
- 用户撤销或修改自动计划的比例；
- 每种模式的重复使用率；
- 开源侧安装成功率、真实 issue 可复现率、外部 Detector 和 Benchmark 贡献。

指标只用于发现流程问题，不替代人工质量评估，也不授权上传用户媒体。

## 15. 明确非目标

- 不覆盖或静默删除源文件；
- 不进行真实人物身份识别或建立身份数据库；
- 不承诺复杂物理真实性判断；
- 不用统一总分裁判艺术质量；
- 不把生成内容描述成恢复的原始信息；
- 不默认上传视频、音频、帧、提示词或报告；
- 不默认下载大型模型；
- 不宣称百分百修复、百分百隐私或法律合规；
- 不在一个版本同时浅层交付四种模式；
- 不为增长删除失败测试、隐藏限制或制造虚假 Benchmark。

## 16. 实施前门槛

本文件是产品组合级方向，不作为一个超大实施计划一次完成。B、C、D 和高级
AI 分别需要独立的功能设计与实施计划。用户通过本规范后，下一份实施计划
只覆盖：正式范围文档变更、共享处理契约和 A Publish Ready MVP。

A MVP 首批提供三个稳定的输出类别：保持原比例的兼容 MP4、9:16 竖屏社交
视频和 16:9 横屏社交视频。具体平台名称映射到有版本的 Profile；平台规则
变化时更新 Profile 和验证数据，不改写历史处理记录。MVP 不启用远程处理。
通过设备预检的小型兼容任务可使用 `browser_local`，其余任务使用
`native_local`；任一后端不具备能力时都必须在执行前阻止任务并说明降级路径。

进入实现计划前必须完成：

1. 用户审阅并确认本书面规范；
2. 把阶段 0 和阶段 1 拆成可独立实施、测试和发布的计划；
3. 在代码实现前更新正式产品范围和架构文档，明确 Resolve 版本边界；
4. 验证首批三个 Publish Profile 的实际参数，并确定浏览器本地执行上限；
5. 为处理计划、动作、产物、确认和复检定义 schema；
6. 用真实小型视频验证候选 FFmpeg 动作，不写死 fixture 名称；
7. 保持基础安装离线、CPU-only，重型模型继续放在可选 extra；
8. 明确公开网站能力不足时的原生本地降级路径。

只有满足这些门槛，才能把“已发现问题”扩展为“已交付可用结果”，同时不
破坏 VideoScope 已有的可解释性、隐私和开源可信度。
