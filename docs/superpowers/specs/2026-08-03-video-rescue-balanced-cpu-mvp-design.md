# Video Rescue Balanced CPU MVP 设计

状态：已通过对话评审，待用户审阅书面规范

日期：2026-08-03

适用范围：VideoScope Resolve B 的首个可发布 CPU MVP

## 1. 设计结论

Video Rescue 面向“视频打不开、播放中断，或者能够播放但观感明显较差”的用户，
交付经过验证的新文件，而不是只列出问题或滤镜建议。

首个 MVP 采用双结果架构：

- `faithful-rescue.mp4` 尽量保留原始可解码内容，只执行结构性安全修复；
- `improved-viewing.mp4` 在保真结果基础上执行经检测触发、预览确认和输出复检的
  CPU 改善。

Video Rescue 必须诚实区分“结构已修复”“观感已改善”“部分内容已抢救”和
“信息无法恢复”。不得宣称百分百恢复，不得把锐化、插值或生成内容描述为原始细节。

本 MVP 完整实现 Conservative 与 Balanced；Aggressive AI 只保留版本化扩展边界，
不安装模型、不下载权重、不生成或补造视频内容。

## 2. 用户与使用场景

### 2.1 目标用户

- 手机或相机视频损坏的普通用户；
- 收到异常导出文件的内容创作者；
- 需要抢救录屏、会议、课程或家庭影像的用户；
- 需要批量、可追溯媒体恢复的工程和研究人员。

### 2.2 症状入口

界面使用用户能理解的症状，而不是编码器参数：

- 视频打不开或播放中断；
- 没有声音或声音过小；
- 画面过暗、噪声重或不够清晰；
- 画面抖动、闪烁、卡住或掉帧；
- 音画不同步；
- 颜色异常；
- 不知道哪里坏了。

用户可以选择多个症状，也可以选择自动检查。症状只是扫描和计划提示，不是未经检测
便执行处理的授权。

## 3. 产品承诺与边界

### 3.1 成功必须交付实际结果

成功状态必须对应至少一个可播放、可下载且通过对应复检门槛的新视频。只产生问题列表、
建议文字、预览或“处理完成”提示不算成功。

### 3.2 原文件与内容边界

- 原文件只读，永不覆盖、移动或静默删除；
- 所有处理写入隔离工作区，最终产物通过暂存目录原子发布；
- 影响内容的裁除、静音、同步偏移和画面处理必须在预览后确认；
- 保真版与改善版独立交付，改善失败不得破坏已验证的保真版；
- 无法恢复的信息必须保留明确标记，不得通过省略记录伪装完整恢复。

### 3.3 本 MVP 不包含

- AI 插帧、超分辨率或生成式补全；
- 凭空重建缺失帧、纯黑细节、过曝细节或削波音频；
- 复杂、随时间变化且无法可靠测量的音画同步猜测；
- 未经检测触发的一键滤镜堆叠；
- 默认网络访问、媒体上传、模型下载或 GPU 依赖；
- 未校准的统一质量分、恢复率或真实世界准确率声明。

## 4. 策略与可恢复等级

### 4.1 Conservative

Conservative 面向重要原片、证据视频和不可接受内容变化的场景，允许：

- 重封装、索引和时间戳规范化；
- 选择有效视频和音频轨道；
- 旋转信息规范化；
- 扫描和保留连续可解码区间；
- 安全裁除无法解码的头部或尾部；
- 校正能够可靠测量的固定音画偏移。

Conservative 不执行主观画面增强。

### 4.2 Balanced

Balanced 是默认策略。它包含 Conservative，并可根据可观察证据提出：

- 受限 Gamma、亮度和对比度改善；
- 低强度、保细节的视频降噪；
- 受控锐化，只改善边缘观感；
- 仅针对连续、非切镜全局亮度波动的闪烁平滑；
- 响度标准化、削波保护和轻度音频降噪；
- 能够可靠测量的固定音画偏移校正；
- 在运动估计可靠且裁切损失受限时的轻度防抖；
- 经用户确认后对冻结或损坏区间保留、裁除或仅标记。

每项动作具有独立配置、适用条件、强度上限、预览、降级路径和复检规则。动作不能
互相调用；依赖关系由计划明确声明并由编排器执行。

### 4.3 Aggressive AI

Aggressive AI 留给后续独立规格，可包含插帧、超分辨率、生成式补全和语音增强。
未来实现必须单独安装与启用、明确允许模型下载、定位全部生成区间，并保持 CPU 抢救
能力可独立使用。

## 5. 处理流程

```text
只读源文件与哈希
  -> 容器、轨道、时间戳和可解码区间扫描
  -> 症状与恢复能力判断
  -> Conservative / Balanced 候选方案
  -> 同时间范围的 5-10 秒原始、保真、改善预览
  -> 用户选择动作、区间和强度并确认计划摘要
  -> 完整 CPU 处理
  -> ffprobe 与适用检测器复检
  -> 原子交付结果包
```

预览是确认产物，不是最终产物。完整处理必须重用已确认计划的版本、参数和摘要；任何
计划变化都使旧确认失效。

## 6. 核心架构

Video Rescue 复用 Resolve 的探测、哈希、命令安全、工作区、确认和原子发布模式，
但建立独立的 `videoscope.rescue` 领域。Publish Ready、Safe Sharing 与 Rescue 不得
相互调用业务逻辑。

### 6.1 RescueScanner

流式扫描容器、轨道、包、时间戳和可解码区间，生成有界且脱敏的诊断摘要。它不把完整
视频读入内存，也不改变源文件。

### 6.2 SymptomClassifier

将用户症状与可观察指标映射为结构化候选症状。其输出必须使用中性语言并保留限制，
不能把启发式观察描述为确定故障原因。

### 6.3 RescuePlanner

根据损坏映射、策略和用户锁定区间生成确定性候选计划。每个动作声明版本、参数、理由、
影响范围、内容变化、确认要求、依赖、资源和失败降级。Planner 不写媒体文件。

### 6.4 PreviewBuilder

从最有代表性的问题区间生成长度不超过 10 秒的原始、保真和改善预览。三者必须覆盖
相同时间范围；预览文件和工作区使用有界资源，不进入最终公开结果包。

### 6.5 RescueExecutor

使用参数数组调用 FFmpeg 或受控本地组件，禁止 `shell=True`。Executor 只写任务工作区，
并按计划顺序执行；动作失败时停止依赖链，但保留已通过验证的独立片段。

### 6.6 RescueVerifier

重新执行 ffprobe 和适用的 VideoScope 检测，检查可解码性、时长、流、同步、黑屏、冻结、
削波、过度裁切和增强副作用。它报告独立检查结果，不合成统一总质量分。

### 6.7 RescueArtifactManager

原子发布最终视频、JSON 和 HTML，维护公开结果与内部诊断信息的边界。报告只引用输出根
目录内的相对路径。

### 6.8 统一核心服务

```text
CLI / Local Web API
  -> RescuePipeline
      -> Scanner
      -> SymptomClassifier
      -> Planner
      -> PreviewBuilder
      -> Confirmation Gate
      -> Executor
      -> Verifier
      -> ArtifactManager
```

CLI 和 Web API 必须使用同一个 `RescuePipeline`，不得复制分析或处理逻辑。

## 7. 数据契约

新增严格、版本化的 Pydantic 模型：

- `RescueRequest`：症状、策略、保留/允许裁除区间、音频偏好和路径外有效配置；
- `MediaDamageMap`：输入哈希、媒体摘要、扫描覆盖及可解码、损坏、不确定和信息缺失区间；
- `RescueAction`：动作 identity、版本、参数、理由、输入区间、影响、确认和降级；
- `RescuePlan`：两套候选动作、预览范围、预期产物和确认摘要；
- `RescueConfirmation`：用户选择并与计划摘要绑定；
- `RescueChangeLog`：实际动作、参数、耗时、退出状态和产物哈希；
- `RescueVerificationReport`：独立复检结果和人工复核原因；
- `RescueTechnicalReport`：状态、损坏映射、产物、限制和复核事项。

模型拒绝未知字段、绝对路径、目录穿越、NaN/Infinity、空区间和反向区间。JSON 使用 UTF-8、
稳定排序和原子写入。同一输入、版本和完整配置产生确定性损坏区间 ID、动作 ID、计划摘要、
证据选择和排序；任务 ID 与创建时间可以变化。

每个输出区间都能追溯至：

```text
输出时间区间 -> 执行动作 -> 源时间区间 -> 扫描证据 -> 用户确认
```

## 8. 产物契约

预览保留在任务的本地复核区，只由当前设备上的工作台读取，不进入最终下载包：

```text
rescue-review-private/
  previews/
    source-preview.mp4
    faithful-preview.mp4
    improved-preview.mp4
```

典型公开结果为：

```text
rescue-output/
  rescue-plan.json
  faithful-rescue.mp4
  improved-viewing.mp4
  damaged-segments.json
  changes.json
  verification-report.json
  technical-report.json
  report.html
```

没有证据支持改善时，Balanced 可以只交付保真版并说明原因；不得复制保真版并把副本冒充
改善版。`partial` 任务可以交付一个或多个连续可播放片段，但必须提供来源映射和未恢复区间。

## 9. 状态与错误处理

任务状态为：

```text
created -> scanning -> planning -> awaiting_confirmation
        -> previewing -> processing -> verifying
        -> completed | partial | needs_review | failed | cancelled
```

- 完全无法探测：不创建伪视频，状态为 `failed`；
- 部分无法解码：尝试从后续关键帧继续，交付可播放片段，状态为 `partial`；
- 单项增强失败：不影响保真版，停止其依赖链并记录降级；
- 防抖过裁切、锐化光晕、降噪失真、亮度削波或其他副作用：改善版进入
  `needs_review` 或 `failed`；
- 同步无法可靠测量：不猜测偏移，保留原同步并提示人工检查；
- 空间不足、取消或外部进程中断：停止新动作，清理未完成临时文件，保留已验证的独立产物；
- 所有错误脱敏，不泄露绝对个人路径、用户名、令牌、未过滤 stderr 或服务端堆栈。

只有对应清单中的最终产物全部通过校验，才进入公开结果目录。工作区、原始损坏数据和
半成品不得混入下载包。

## 10. 用户体验

扫描后，页面展示可解码时间占比、明确损坏和不确定区间、两种策略差异以及无法恢复的信息。
“可解码时间占比”只描述已扫描时间区间，不代表视觉质量或恢复成功率。

用户可以切换同步预览、逐项启停改善、选择有限强度、锁定必须保留区间，以及决定损坏区间
保留、裁除或只标记。确认页展示所有内容变化和不可逆结果，但原文件始终可找回。

结果页提供保真版与改善版下载、同步前后对比、损坏时间轴、独立前后指标、无法恢复说明、
人工复核入口及 JSON/HTML 报告。移动端保留上传、扫描、预览、确认和下载主流程；高级参数
折叠。界面支持英文和简体中文，`what912` 标识不参与语言切换。

## 11. 验证规则

至少验证：

- 输出能够完整解码，容器与流信息合法；
- 输出时长和源映射符合已确认计划；
- 固定同步校正与计划一致且未引入反向偏移；
- 无新增严重黑屏、冻结或高频闪烁；
- 亮度改善没有不可接受的高光/暗部削波；
- 降噪与锐化没有越过配置和副作用门槛；
- 防抖裁切、边界和分辨率符合计划；
- 音频响度、峰值和轨道存在性符合计划；
- 输出哈希、相对路径、来源映射和变更记录一致。

验证失败绝不产生 `completed`。只有保真版通过时，可以独立发布保真版，并把改善版标为
`needs_review` 或 `failed`。

## 12. 测试策略

### 12.1 契约测试

覆盖非法区间、未知字段、路径穿越、摘要篡改、计划确认绑定、确定性排序、JSON 往返，以及
带空格、中文和 Unicode 的路径。

### 12.2 算法与命令测试

覆盖时间戳异常、轨道选择、损坏头尾和中间区间，以及亮度、降噪、锐化、闪烁、响度、固定
同步和防抖动作的正例、负例、边界、取消和故障注入。生产逻辑不得识别 fixture 文件名。

### 12.3 可复现 fixture

用本机 FFmpeg 或程序生成正常、容器异常、尾部损坏、中间不可解码、过暗、噪声、轻度模糊、
闪烁、抖动、低音量、音频噪声、削波和固定音画偏移视频。不下载素材，不提交大体积生成视频；
缺少 FFmpeg 时明确跳过或报出可理解错误。

### 12.4 端到端与分发测试

覆盖 Conservative、Balanced、预览确认、部分抢救、取消、空间不足和动作失败；确认 CLI 与
Web 共用核心 Pipeline；重复运行除任务 ID 和时间外保持确定；公开 JSON 不包含绝对路径。

统一执行 Python 验证、前端测试与构建、wheel/sdist 构建、产物审计和干净虚拟环境真实抢救
烟雾测试。基础路径不得联网、下载模型或依赖 GPU。

## 13. CPU MVP 验收标准

- 对部分损坏输入实际交付可播放片段和精确未恢复区间；
- 对典型暗部、视频噪声、音量和固定同步问题产生可观察、可复检的改善；
- 正常输入不会因默认处理发生显著退化；
- 保真版始终独立于改善版；
- 未通过复检的改善版不会显示为完成；
- 所有裁除、增强、失败和不可恢复区间可追溯；
- 原文件未改，公开产物不泄露个人绝对路径；
- 基础安装离线、CPU-only，不下载模型；
- 不虚构恢复率、准确率、性能数据或测试结果。

合成 fixture 仅用于工程回归。真实效果结论必须来自实际运行与独立人工标注集。

## 14. 实施顺序

1. 冻结正式产品、架构、路线图和 Rescue JSON 契约；
2. 建立扫描器、损坏区间模型和可复现损坏 fixture；
3. 实现 Conservative 计划、预览、执行、复检与 CLI 闭环；
4. 实现 Balanced 的独立 CPU 动作及副作用门槛；
5. 实现确认绑定、部分抢救和原子产物发布；
6. 接入本地 Web API、双语工作台和同步对比；
7. 完成端到端、分发、干净安装、性能和人工验收；
8. 独立审查后再决定是否合并、推送或发布。

## 15. 发布前人工检查

- 用真实手机、相机、录屏和异常导出文件验证，而不只依赖 synthetic fixtures；
- 人工确认改善版在代表性设备与播放器中没有明显退化；
- 复核 Windows、Linux 和 macOS 的 FFmpeg 能力差异与防抖降级；
- 确认所有用户可见文案严格区分修复、改善、裁除和无法恢复；
- 确认公开网站无法在没有真实本地处理后端时模拟抢救成功。
